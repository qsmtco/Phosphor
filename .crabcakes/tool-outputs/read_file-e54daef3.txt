10|## 1. What Phosphor is
11|
12|An **agent-native phone operating system**: a GrapheneOS-derived Android platform in which the AI agent is the primary interface and a system coordinator, not an app. The user speaks; the agent resolves intent, calls the appropriate platform capability, and renders the active screen as HTML/JavaScript in real time. Home, notifications, calls, messages, settings, camera and sensors all flow through that one agent-controlled surface.
13|
14|One-sentence definition (from the vision): *Phosphor is a GrapheneOS-based, voice-first, agent-native phone operating system whose agent designs and renders the active HTML/JavaScript interface in real time, allowing Captain JAQ to use the Pixel as a coordinated team member.*
15|
16|- **Target device:** Google Pixel 8a, codename `akita`, model GKV4X (international, not carrier-locked). Serial `3C121JEKB03922`.
17|- **Target foundation:** GrapheneOS-derived image, our own signing keys, our own AVB root of trust.
18|- **Development host:** `qoder` (Linux) + USB to the Pixel.
19|
20|### What Phosphor is NOT
21|
22|Do not redirect this project into any of these because they are easier:
23|
24|- a normal Android app that calls the stock Phone/Messages apps;
25|- a chatbot floating on top of GrapheneOS;
26|- a browser shell presented as the final product;
27|- a Termux-hosted runtime presented as the operating system;
28|- a Debian VM presented as the OS;
29|- a collection of loosely connected apps with an AI front-end.
30|
31|The repo's pre-existing material — the copied DragonCakes-derived Python agent runtime, the Python HTTP runtime, the browser shell, local Whisper, the Rust bridge, Termux/:API/:Boot, Tailscale/SSH, the on-device workspace — is **prototype and bring-up material only**. Commit `a1dc69a` marks those PoC-era architecture decisions as superseded. `docs/VERIFICATION.md` verifies the **iOS proof-of-concept** (2026-09-04, front-end-agnostic trust requirements); it is not Android/GrapheneOS verification.

76|### adb vs MTP — the trap that costs an hour
77|
78|A Pixel with USB debugging OFF enumerates as MTP only and `adb devices` is empty. That is a USB descriptor fact, not an authorization state — no amount of authorizing, re-plugging or udev fixing will make adb see it. Check the PID, not `adb devices`:
79|
80|| PID | mode |
81||---|---|
82|| `4ee1` | MTP — debugging OFF; adb cannot see the device at all |
83|| `4ee2` | MTP + adb |
84|| `4ee5` / `4ee6` | PTP / PTP + adb |
85|| `4ee7` | adb only |
86|| `4ee9` | MIDI + adb |
87|| `4ee0` | fastboot (bootloader mode) |
88|
89|After enabling USB debugging, **replug the cable** — USB does not renegotiate its descriptor set without a reconnect, so an already-plugged phone keeps reporting the old PID. Authorization is per-host RSA key in `~/.android/adbkey` and never carries over from another machine.

93|## 4. The host: `qoder`
94|
95|- Ubuntu **26.04.1 LTS**, Ryzen 9 9950X (32 threads), 59 GiB RAM, 1.8 TB ext4 root with ~1.4 TB free.
96|- **Distro decision (2026-09-24): proceed on 26.04 (Option E).** GrapheneOS officially supports Arch, Debian bookworm, Ubuntu 24.10 and 24.04; 26.04 is unsupported but nothing enforces it, and the full build succeeded. **Never propose downgrading the host distro** — there is no supported reverse path (an in-place reverse would leave a hybrid system). If a distro-specific build failure ever appears, the fallback order is (A) a `systemd-nspawn` container of Debian bookworm/Ubuntu 24.04, then (B) Docker/Podman (usually needs `--privileged` for AOSP's namespace build sandbox). Record the failure before switching.
97|- **`sudo` requires an interactive password** — an agent cannot install packages or run privileged commands. Pattern: write an idempotent script, hand the user `sudo bash <script>`, then verify the result independently.
98|- **No disk encryption** (plain ext4 root, `/swap.img` swap, zero LUKS). Consequences: secrets staged in tmpfs can be paged out to disk, and plaintext credentials on disk are a real exposure. **Run `sudo swapoff -a` before signing and `swapon -a` after** — swap defeats the guarantee that keys return to rest when signing ends.
99|- **No GitHub credential.** No token, no `~/.git-credentials`, no credential helper, no SSH key. `qsmtco/Phosphor` is public, so anonymous reads succeed and make the host *look* authenticated when it is not. The user primes git's in-memory cache as one typed line when a push is needed; never `credential.helper=store` on this host.
100|
101|### Toolchain (all verified on this host)
102|
103|- **`repo`**: the self-updating standalone at `~/.local/bin/repo` (host Python 3.14.4 runs it fine) — not the apt package.
104|- **`adb` / `fastboot`**: Google platform-tools at `~/android-sdk/platform-tools`, never apt (distro packages ship development snapshots and clobber the version scheme). fastboot must be ≥ 35.0.1.
105|- **`adevtool`** needs Node.js 24 LTS, kept side by side at `~/android-sdk/node24`. That install migrates adevtool to the newest Yarn, dirtying `package.json`/`yarn.lock` and adding `.yarnrc.yml` + `.yarn/` — harmless, do not mistake it for corruption.

127|## 5. Signing keys, custody, and identities (public values only)
128|
129|The key set is **permanent** — the AVB key cannot change without another wipe. It is **10 private keys** (GrapheneOS's own set from `script/common.sh`): `bluetooth gmscompat_lib media networkstack nfc platform releasekey sdk_sandbox shared` plus `avb.pem`. APK keys are RSA 4096; the passphrase is identical across all keys; `make_key`/`encrypt-keys` use scrypt + AES256.
130|
131|Custody model: **one key set; the YubiKey gates access rather than performing the signing.** The mechanism that makes token-gating work with zero patching: `script/decrypt-keys` only prompts when the `password` variable is undefined, so a wrapper unwraps the passphrase via the token, exports it, and GrapheneOS's own flow runs untouched. `generate-release.sh` is file-based (`sign_target_files_apks -o -d "$KEY_DIR" --avb_vbmeta_key "$KEY_DIR/avb.pem"`), so supplying key files is the flow's native mode.
132|
133|Why the token is not the signer: PIV has 4 usable primary slots for 10 keys, and RSA-4096 signatures on the token are slow and serial across the thousands of APKs a release signs. RSA key size is **not** a constraint (fw 5.7+ supports RSA-3072/4096 in PIV). If signing must ever be hardware-bound, a YubiHSM 2 (~$650) supports RSA 4096 and PKCS#11; `avbtool` has `--signing_helper` and `SignApk.java` references PKCS#11.
134|
135|Public identities to check artifacts against:
136|
137|| Value | sha256 |
138||---|---|
139|| `avb_pkmd.bin` | `2256f03c5d5189debf9466e6dfb8a63d2f66e8abb96f10c074cc289ccb36b602` |
140|| Platform certificate | `4bcb40d3c470ee9346df9954276294904b0db167f317c940714872b5d6c74a96` |
141|| Flashed `vbmeta.img` digest (first 7488 bytes) | `bd17532d485543cabba4d54796461d3c972df9c8d7161930a68d0a0a1d9cf127` |
142|| Vanadium (browser/WebView) signature | `c6adb8b8…`, DN `CN=GrapheneOS` — **not ours**, see below |
143|
144|**Vanadium carries GrapheneOS's signature, not ours — expected, and load-bearing.** `external/vanadium` ships prebuilt, already-signed Trichrome/WebView APKs; `generate-release.sh` re-signs AOSP/APEX components to our keys but leaves these alone. Do **not** "fix" it by re-signing them: they are GrapheneOS's component under GrapheneOS's trust anchor. Since the browser/WebView is Phosphor's intended *shell*, owning that signature requires building Chromium from source — an architectural decision for Phase 4, not a build tweak. Check APK signatures against `com.android.settings` or `com.android.shell`, never Vanadium.
145|
146|**Where keys live:** at rest in `keys/<device>/` (keep it OUTSIDE the source tree — 1057 git repos is the last place a private key belongs; mode 0700); during signing in `mktemp -d /dev/shm/...` so plaintext exists in RAM only, removed by an EXIT trap. **Never back up the encrypted key files without the means to unwrap them** (the wrapped passphrase blob + a reproducible/escrowed PIV key) — that yields a backup that looks complete and is worthless.
