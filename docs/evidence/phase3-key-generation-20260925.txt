VERIFICATION PERFORMED
----------------------

All checks were run independently of the generating script, against real output.

  1. Encryption          Every one of the ten keys REFUSES a wrong passphrase
                         (openssl pkcs8 -passin pass:wrong fails on all of them).
  2. Format              openssl asn1parse on a .pk8 shows PBES2, i.e. genuine
                         scrypt-encrypted PKCS#8 rather than a mistakenly
                         unencrypted file.
  3. Certificates        Nine distinct certificates (9 unique of 9), each RSA-4096,
                         subject CN=Phosphor/O=Phosphor/C=US.
  4. avb_pkmd.bin        Structurally verified against avbtool's own encoder
                         (AvbRSAPublicKey.encode): 1032 bytes = 8 + 2*(4096/8),
                         key_num_bits = 4096, n0inv recomputed from the modulus
                         matches, rr == (2^4096)^2 mod N matches, and the modulus
                         is genuinely 4096 bits. Note this format has NO trailing
                         hash — the earlier assumption that it did was wrong.
  5. Seal / unseal       The token unsealed the passphrase through PKCS#11 using
                         RSA-PKCS-OAEP with hashAlg=SHA256 and mgf=MGF1-SHA256,
                         confirming both sides agree on the OAEP parameters.
  6. Agreement           The token-unsealed passphrase EQUALS the escrow copy
                         (64 characters each). This is the check that proves the
                         escrow is not a decoy: if they had diverged, the escrow
                         would have been worthless exactly when it was needed.
  7. Key/cert pairing    platform.pk8 was decrypted with that passphrase
                         (Private-Key: 4096 bit, 2 primes), and openssl rsa
                         -pubout on it matched platform.x509.pem exactly —
                         confirming .pk8 and .x509.pem are a genuine pair.

All plaintext material created during verification (unsealed passphrase,
decrypted private key, derived public keys) was shredded afterwards.

THE FLASH — 2026-09-25
======================

The signed build was flashed to the device. Pre-flight per
docs/PHASE-3-FLASHING-AND-RECOVERY.md §2.

  P1  fwupd stopped            required EVERY session: it came back with a device
                               replug mid-session and had to be stopped again.
  P2  fastboot 37.0.1          at ~/android-sdk/platform-tools
  P3  udev rules present
  P4  flashing as non-root     no sudo used for fastboot itself
  P5  device authorized        3C121JEKB03922, product akita
  P6  device reaches bootloader  exercised
  P7  OEM unlocking permitted  FAILED first — see below
  P9  USB mode transitions     FAILED first — the significant one, see below

P7 — get_unlock_ability returned 0, then 1
  The first bootloader session reported get_unlock_ability: 0. The cause was
  mundane: the Settings > System > Developer options > "OEM unlocking" toggle was
  off. Enabling it on the device flipped the value to 1 on the next bootloader
  session with no other change. A 0 here means "go enable the toggle" — it is NOT
  a carrier lock or a hardware restriction. Easy to misdiagnose as fatal.

P9 — a PORT fault, not a driver or permissions fault
  From the original port (Bus 005) `adb reboot bootloader` worked every time, but
  after `fastboot reboot` the device never came back: it vanished from lsusb
  ENTIRELY — not merely from adb — on 2 attempts out of 2, and was still absent
  120 s later. A replug into the SAME port did not fix it. Moving the device to a
  different port (Bus 001, usb:1-6.2) gave clean passes on all three transitions:
  adb->bootloader 14 s, fastboot->fastboot 6 s, fastboot->Android 44 s.

  This matters because flash-all.sh runs `fastboot reboot-bootloader` BETWEEN
  flashing the bootloader to the other slot and flashing the OS. A device that
  drops off the bus there leaves the bootloader half-flashed with the active slot
  already switched — recoverable, but the worst possible place to stop. The
  rehearsal touches no partition and is now a standing pre-flash requirement
  (doc §2.5).

  Evidence the rehearsal is itself non-destructive: the device state was
  re-measured afterwards and matched the pre-rehearsal baseline exactly —
  locked=1, verifiedbootstate yellow, incremental 2026091901, patch 2026-09-01,
  with no change to the fingerprint.

KEY BACKUP — done BEFORE the flash, deliberately
  Script    scripts/keys-backup-escrow-usb.sh
  Result    24 files, ~100 KB, at
            /run/media/cptjaqx/PHOSPHOR-ESCROW/phosphor-keys-akita-20260925T151545Z
  Verified  20/20 key files hash-identical to the host; every .pk8 still
            encrypted PKCS#8 (no plaintext reached removable media);
            avb_pkmd.bin sha256 matches the recorded value; MANIFEST.txt records
            the hashes and the recovery steps.

  Order matters: before the flash, losing the key set costs nothing (regenerate
  and re-sign). After it, the AVB key is PINNED to the device, so a lost key set
  means another wipe to adopt a new one.

  Three real bugs in the backup script were caught by its own guards:
    - `blkid -L` reported /dev/sda1 while the USB was UNPLUGGED (stale cache).
      A device path that can point nowhere is the wrong basis for a key copy.
      Now reads live sysfs, then verifies the node exists.
    - RM and TRAN are DISK properties; asking on the partition returns empty
      strings, so a perfectly good drive failed the guard.
    - The "is it still encrypted?" test was a FALSE NEGATIVE: `openssl pkcs8
      -passin pass:wrong` exits non-zero for a PLAINTEXT key too, so it would
      have happily copied raw signing keys. Now tests the DER structure instead
      (EncryptedPrivateKeyInfo has a constructed SEQUENCE at depth 1; a plaintext
      PrivateKeyInfo has a primitive INTEGER).
    Also, mkfs.ext4 leaves the filesystem root owned by root, which only shows up
    later as a bare "mkdir: Permission denied"; the format script now chowns it.

  Platform-signed apps carry our key, as intended. Vanadium does not, and that is
  expected rather than a signing failure: GrapheneOS ships Vanadium as PREBUILT,
  already-signed APKs in the platform_external_vanadium project (external/vanadium,
  1.1 GB, pinned to their tag 2026091900, remote grapheneos-gitlab). They carry
  GrapheneOS's own release key. generate-release.sh re-signs AOSP and APEX
  components to our keys, but not these pre-signed APKs.

  Recorded plainly, because it is an architecture fact rather than a detail: the
  browser and WebView — which the Phosphor design treats as the SHELL, not as a
  peripheral — are GrapheneOS's binaries under GrapheneOS's trust anchor, not ours.
  The signature cannot be claimed without building Chromium from source and signing
  it ourselves, which is a large separate undertaking belonging in the platform
  architecture (Phase 4), not in the flashing procedure.


RECOVERY PATH (RUNG 2) — TESTED 2026-09-25
==========================================

Re-ran flash-all.sh over the working install, to prove the recovery path before it
was ever needed rather than discovering its behaviour during an emergency.

  Result   exit 0; the device booted our build again afterwards.
  Method   a marker file planted in /sdcard before the run, a userdata setting
           (screen_off_timeout = 30000), and the identity properties — all read
           back afterwards to distinguish "recovered" from "recovered and wiped".

CORRECTION — flash-all.sh DOES WIPE USERDATA
  The marker was GONE afterwards and the device came up at the setup wizard. The
  installed script does it explicitly:

      fastboot erase userdata      (line 108)
      fastboot erase metadata      (line 109)

  An earlier revision of PHASE-3-FLASHING-AND-RECOVERY.md claimed the opposite —
  that the wipe came only from the unlock, and that a reflash over an existing
  install preserves data. It survived unnoticed because the FIRST flash happened
  immediately after the unlock wipe, so a second wipe was indistinguishable from
  the first. The marker test exists precisely to tell those two apart, and it did.

  Consequence: rung 2 of the recovery ladder is a DATA-LOSS recovery. Reflashing
  restores the device, not the data.

OTHER FINDINGS FROM THE SCRIPT
  - It erases and then writes avb_custom_key (lines 92-93):
        fastboot erase avb_custom_key
        fastboot flash avb_custom_key avb_pkmd.bin
    So OUR AVB public key is installed into the device's custom-key partition.
    That is what lets the bootloader verify our images on an unlocked device, and
    it is why the vbmeta digest comparison above is meaningful.
  - It hardcodes --set-active=a (line 83), commented as being because the super
    partition layout depends on the current slot. A flash therefore always ends on
    slot A, whichever slot it started from — which is why the device reports
    ro.boot.slot_suffix=_a.
  - It also erases fips, dpm_a and dpm_b, disables uart, and cancels any pending
    snapshot update. The recurring "skip copying super image avb footer due to
    sparse image" warning is normal, not an error.

D4 SHOULD BE REVISITED
  The key-management design's D4 ("never relock") rested partly on the assumption
  that verified boot could not be enforced under our own key. avb_custom_key is
  exactly the mechanism for doing that on a Pixel, so relocking with OUR key may
  be achievable. It would still cost a wipe, and still carry the risk that a
  non-booting build plus a locked bootloader equals a brick (recoverable only by
  unlocking again, which wipes). This warrants a deliberate review, not a casual
  step — and it is recorded here rather than acted on.
